### ❌ 真 FAIL（2 项，均为同一条：PROPFIND 坏 body 应 400 实返 207）
```

     --data-binary 'not xml at all'   https://webooks.cszxorx.dpdns.org/dav/   → 207（期望 400）
curl -X PROPFIND -H "Depth: 0" -H "content-type: application/xml" \
```

**无安全/成本影响**（坏 body 换来一次正常 allprop 响应），属合规细节缺陷。
litmus 论调：`<a/><b/>` 双根元素、非 XML 文本都必须 400。
**处置：本轮不修**（要动 PROPFIND 解析入口 + 全量重验，收益仅两条断言）；已记入
docs/review-2026-10-13.md §八遗留清单。修法建议：`parsePropfindBody` 入口加最小
良构性检查（body 无任何标签或首个根元素闭合后仍有非空白内容 → 400），复用
locks 解析已有的标签配对检查思路。

## 4.1 🔴 发现 A：匿名锁会挡住「天真客户端」的写路径（拒绝服务）—— 线上已实证

> **⚠️ 本小节于 2026-10-17 00:1x 修订（定性下调）**：初版写作「可直接阻断全站写入」，
> 措辞过强。Lead 独立复现时发现了关键反证 —— **锁令牌本身是匿名可读的**，
> 任何会读 XML 的调用方都能自救（详见 4.5）。准确表述是：
> **默认/天真的客户端会被挡住（上传器不发 `If` 头），会读 PROPFIND XML 的能自行绕过**。
> 它仍然必须修（默认路径就被打断，且是零成本匿名触发），但不是「硬锁死」。
> 第五节给出两条**新的**缓解事实（第三方可解除他人锁），严重度进一步下调。

**这不是 litmus 断言里的条目**（litmus `locks` 套件因 MKCOL 阻塞从没跑起来），
是在等价重放 `locks` 时顺手发现并深挖的。

**最小复现（线上，无需任何凭据）**：
```bash
U=https://webooks.cszxorx.dpdns.org
# 1) 匿名对某个公开集合加锁（LOCK 端点没有任何口令/节流门禁）
curl -X LOCK "$U/dav/%E6%9C%80%E8%BF%91%E6%94%B6%E5%BD%95/" \
  -H "Timeout: Second-60" -H "Content-Type: application/xml" \
  --data '<?xml version="1.0"?><D:lockinfo xmlns:D="DAV:"><D:lockscope><D:exclusive/></D:lockscope><D:locktype><D:write/></D:locktype></D:lockinfo>'
# → HTTP/2 200 + lock-token: <urn:uuid:...>

# 2) 此后该集合内的一切写入全被 423 挡住
curl -X PUT "$U/dav/%E6%9C%80%E8%BF%91%E6%94%B6%E5%BD%95/x.epub" ...      # → 423 Locked
curl -X DELETE "$U/dav/%E6%9C%80%E8%BF%91%E6%94%B6%E5%BD%95/某本书.epub" \
     -H "Authorization: Bearer $正确写口令"                                    # → 423 Locked（口令无效！）
```

**五个顶层集合（按书名/按作者/按类型/按格式/最近收录）全部接受匿名 LOCK，实测全 200。**
一次性给这 5 个集合各加一把锁，则**这 5 个集合（及其子树）的一切写入对「不发 `If` 头
的客户端」全部 423**（实测 `PUT → 423` × 4，第 5 个因连接抖动返回 000）。
**注意「对谁生效」**：不发 `If` 头的天真客户端（rclone / Finder / 网页表单式上传器）
一律被挡；而**任何会读 PROPFIND XML 的调用方都能拿到锁令牌并自行绕过**（4.5 节实证）。
所以准确说法是「**默认路径被打断**」，不是「全站写死」。

**为什么写口令挡不住**：`src/lib/locks.ts` 的 `liveLockForResource()` 只按**资源路径**
找活锁，不看锁的 owner；`src/webdav/index.ts:148` 的 `handleLockedWrite()` 判断
「`If:` 头里的令牌 == 活锁令牌」才放行。攻击者不需要知道写口令 ——
**他拿的是自己的锁令牌，而合法客户端拿的是写口令，两者根本不在一套凭据体系里**。

**续期无上限（经 Lead 裁定为预期行为）**：`LOCK` + `If: (<自己的 token>)` +
`Timeout: Infinite` → 200（实测），TTL 刷到 `INFINITE_LOCK_SECONDS = 3600`（1 小时，
`src/lib/locks.ts:35`）。RFC 4918 §10.7 只要求服务端 MAY 限制 Timeout，
§10.2.4 允许把 `Infinite` 兑成有限时长 —— **「能刷新」不是缺陷，缺陷是「谁能刷新」**：
匿名者能建锁自然能刷新。口令闸门（修法 ①）加上后此条自动闭合，不必额外改。

**放大面（设计细节，非缺陷但影响严重性）**：集合锁**按前缀覆盖整个子树** ——
锁 `/dav/按书名/` 会让 `/dav/按书名/S/三体.epub` 这种深层桶里的书**也**写入 423
（本地实测 `PUT S/deep.txt → 423`、`PUT S/三体.epub → 423`）。所以 **5 把锁就够覆盖全库**。

**明确不是缺陷的部分**（避免误判）：
- 根锁 `/dav/` **不传播**到子路径（`liveLockForResource` 的 SQL 显式排除 `resource != '/'`，
  源码注释原话「根锁会前缀匹配整个库，任意客户端对根加个锁就锁死全站上传」）——
  实测锁根后 `PUT 最近收录/rootlock.txt → 201`。**设计者想到了这一层，但只堵了根，
  没堵集合**，而集合锁的前缀传播是同样的效果。
- **读路径完全不受影响**：锁只挡写（`src/webdav/index.ts` 注释「锁只挡写，不挡读」）——
  实测加锁期间 `PROPFIND → 207`、R2 直链照常服务。所以这**不会**让书库变只读不可用，
  是「**只阻挡写入**」的拒绝服务。
- **网页上传通道（`/api/upload/*`）不受锁影响**（`src/api/upload.ts` 无任何 lock 引用）。
  受损的是 WebDAV 客户端写入（rclone/Finder 挂载上传）。

**文档覆盖情况**：`docs/security-audit.md:164` 只记录了「匿名 LOCK 端点可无限写入 →
锁表膨胀」，修法是 `sweepExpiredLocks()` —— **那是表膨胀，不是写阻断**。
**没有任何文档记录「匿名锁能阻断写」**这个风险。

**修法建议（不自修，等裁决）**，按代价从低到高：
1. **LOCK 要求写口令**（`hasWriteToken`），与 DELETE 一致 —— 一行分发层改动。
   代价：WebDAV 挂载时 Windows/Finder 会先 LOCK，无口令的只读挂载会受影响；
   但本站写路径本来就要口令，只读场景不需要 LOCK，**看起来代价可接受**。
2. 给 LOCK 加 `guardWrite` 节流（与 PUT/COPY 一致），至少抬高滥用成本。
3. 给锁的创建加每 IP 上限 / 活锁总数上限（D1 查询计数），防「换路径绕开」。
4. 最保守的缓解：把集合锁（尾斜杠路径）的**前缀传播**限制为显式 `Depth: infinity`
   才生效，`Depth: 0`（默认被本站解析为 `infinity`，见 `handleLock` 的 `depthMatch` 缺省值）
   不覆盖子树 —— 能挡住「5 把锁封全站」，但挡不住「对每个叶子逐把加锁」。

## 4.5 ⭐ 关键修正：锁令牌是**匿名可读**的，且第三方可解除他人锁

**这一节推翻了 4.1 初版的严重度定性**，由 Lead 独立复现时发现，我随后做了原子化复验
（全部证据在同一步骤内取得，见下）。

### 4.5.1 锁令牌匿名可读 → 天真客户端被挡，会读 XML 的能自救

```
PROPFIND /dav/按类型/  (Depth:0, 不带任何 Authorization 头, 请求 <D:lockdiscovery/>)
  → 207，XML 里 locktoken 出现 2 次、urn:uuid 出现 1 次
  → 读出的 token 与锁持有者手里的一致：YES
```
实测（同一步骤内，`Timeout: Second-45`）：
```
LOCK 匿名                    → 200  token=<urn:uuid:93940dc2-...>
PUT  不带 If                 → 423   ← 天真客户端被挡
PROPFIND 匿名读 XML           → 207   拿到同一个 urn:uuid（无需凭据）
PUT  带 If:(公开读出的 token) → 415   ← 锁检查已放行（415 只是扩展名白名单挡的）
```
→ **定性修正**：这不是「硬锁死」，而是「**打断默认路径**」。
不会发 `If` 头的上传器（rclone / Finder / 网页上传壳）会被 423 挡住；
任何愿意多读一次 PROPFIND 的调用方都能自行绕过。
仍须修（默认路径即被零成本匿名打断），但严重度描述必须这样写才准确。

### 4.5.2 第三方可以解除**别人的**锁（Lead 与我都未预期）

```
UNLOCK /dav/按类型/  Lock-Token: <公开读出的 token>   → 204   ← 成功释放他人（匿名者）建立的锁
UNLOCK /dav/按类型/  Lock-Token: <同一 token> + If: <同一 token>  → 409   ← 反而失败
UNLOCK /dav/按类型/  Lock-Token: <原 token>            → 409（此时锁已被上一条释放掉）
```
判读：**`handleUnlock` 只校验 `Lock-Token` 头，不校验请求者身份**，所以任何能从
PROPFIND 读到 token 的匿名访客都能**替别人解锁**。这有两面性：
- **缓解面**（对 4.1 有利）：攻击者锁住集合后，任何第三方（包括被挡住的合法上传者）
  都能一键解除 —— 所以「无限期封禁」不成立，最多是**每次刷新后被路人解除一次**的拉锯。
- **缺陷面**（独立于 4.1）：`docs/webdav-rfc-audit-2026-10-14.md` 的 🔴-8 只记了
  「UNLOCK 不带 `Lock-Token` 静默释放并返 204（§9.11.1 要求 400）」，**没记**
  「谁都拿读到的 token 就能解别人的锁」。RFC 4918 §9.11 假定锁令牌是**私密凭据**，
  而本站把它放在了匿名可读的 `lockdiscovery` 里 —— 两条叠加后「锁」失去了排他性。
  → 修法 ①（LOCK 要口令）之后，建议**同时**把 `lockdiscovery` 里的 `locktoken`
  限定为「仅锁持有者可读」，否则口令闸门只堵了造锁、没堵解他人锁。

### 4.5.3 复验时的干净度（自证无残留）
```
PROPFIND /dav/按类型/leakprobe.probe  → 404   全程只用白名单外扩展名（.probe），从未落盘
解锁后 PUT 不带 If                    → 415   （已回到「仅被白名单挡」的常态）
最终活锁数（PROPFIND /dav/ 数 urn:uuid）→ 0
```
**方法论注记（我与 Lead 都踩过）**：锁有 TTL，**验证必须在一个步骤内完成**
（LOCK→PUT→PROPFIND→UNLOCK→PUT 同脚本，`Timeout` 给足 45~300s）。
跨工具步骤、中间隔几分钟再 PUT，会因锁过期而**假阴性**（Lead 首次复现就是这样
得到 201、差点误判「锁不生效」）。

## 4.6 ⭐ 发现 E：`lockdiscovery` 的 `<D:href>` 多带了一对尖括号（规范跟随的客户端无法解除自己建的锁）

**结论**：服务端内部把锁令牌存成**带尖括号**的字符串 `<urn:uuid:…>`（`src/lib/locks.ts:85`
`return \`<urn:uuid:${b}>\``），于是锁发现响应 `<D:locktoken><D:href>` 里给出的「锁令牌」多了一层括号。
RFC 的规范形态是**裸 URI**，尖括号只属于**头部**：

- §10.1（`refs/rfc4918.txt:3857`）`Coded-URL = "<" absolute-URI ">"` —— 尖括号是**头部/DAV 头**的包装语法；
- §10.5（`refs/rfc4918.txt:4278`）`Lock-Token = "Lock-Token" ":" Coded-URL` → 头部**必须**带括号；
- §14.7（`refs/rfc4918.txt:4609+`）`href`「MUST contain a URI or a relative reference」（Value: `Simple-ref`）—— 是 URI 本身，不是 Coded-URL；
- **§9.10.7 的官方例子**（`refs/rfc4918.txt:3577-3579`）把两者摆在一起，对照最清楚：

  ```
  Lock-Token: <urn:uuid:e71d4fae-5dec-22d6-fea5-00a0c91e6be4>      ← 头部：带括号
  ...
        <D:locktoken>
          <D:href>urn:uuid:e71d4fae-5dec-22d6-fea5-00a0c91e6be4</D:href>   ← XML：裸 URI
        </D:locktoken>
  ```

  即**同一个令牌**：头部带括号、XML 里不带。我们把括号当成了令牌本体，两端都存带括号的串，
  于是在 XML 侧多出一层；规范跟随的客户端据此拼头部 `"<" URI ">"` 就得到 `<<urn:uuid:…>>` →
  服务端逐字符串比较失配 → `409`。

### 4.6.1 四环证据链

| # | 位置 | 事实 |
|---|---|---|
| ① | `src/lib/locks.ts:82-86` `newLockToken()` | 返回的 token **自带**尖括号：`` `<urn:uuid:${b}>` `` |
| ② | `src/lib/locks.ts:354` | `<D:locktoken><D:href>${escapeOwner(lock.token)}</D:href></D:locktoken>` —— 把带括号的 token 直接塞进 `href`，只做实体转义，**不剥括号** |
| ③ | 服务端所有比较都按**带括号**形态 | `src/webdav/index.ts:179` `ifTokens.includes(lock.token)`（`If:` 里抓到的 `/<urn:uuid:[0-9a-f-]+>/`）与 `:339` `live.token !== tokenHeader`（`Lock-Token` 头逐字符串比） |
| ④ | neon（litmus 的 HTTP 库）两条路径**不对称** | `ne_locks.c:588` `if (token[0] == '<') token++;` —— **从 LOCK 响应头读 token 时剥括号**；`ne_locks.c:493` `l->token = strdup(cdata)` —— **从 XML `href` 读 token 时不剥** |

→ 同一台服务器上，`Lock-Token` 头路径可用、**XML `href` 路径不可用**。

### 4.6.2 线上决定性复现（HTTP 状态码逐步留痕，`/tmp/finding-e.txt`）

```
STEP1 匿名 LOCK /dav/按格式/ (Timeout: Second-90)   -> 200
      Lock-Token 头（RFC §10.5 Coded-URL）= <urn:uuid:da0abbd3-3021-46da-a6a0-3b42ab54c9a2>   ← 形态正确
STEP2 匿名 PROPFIND Depth:0 <D:lockdiscovery/>      -> 207
      XML 源码里的 href 文本 = '&lt;urn:uuid:da0abbd3-…&gt;'
      标准 XML 解析器（Python ElementTree）读出的 href = '<urn:uuid:da0abbd3-…>'   ← 多了一对括号
      RFC 例子应为（裸 URI）                          = 'urn:uuid:da0abbd3-…'
STEP3 规范跟随客户端：href 是 absolute-URI，头部必须写成 "<" URI ">"
      UNLOCK Lock-Token: <<urn:uuid:da0abbd3-…>>    -> 409
      body: <D:error xmlns:D="DAV:"><D:lock-token-matches-request-uri/></D:error>
      （若 href 本应是裸 URI，这里应该是 204 —— 多出来的那对尖括号来自服务端）
STEP4 清场
      UNLOCK <urn:uuid:da0abbd3-…>（单括号，服务端内部形态）-> 204
      最终活锁数（PROPFIND /dav/ 数 urn:uuid）        -> 0
```

### 4.6.3 影响面（为什么算真 bug 而不是「客户端怪癖」）

- **只读锁发现链会断**：任何「LOCK → 从 `lockdiscovery` 拿 href → 用它 UNLOCK/续期」的客户端
  都会拿到 `409`。RFC §9.10.1 定义的 `lockdiscovery` 正是**为**这种客户端准备的（写操作不带 token 时服务端返回 423 +
  `lockdiscovery`，客户端据此发现该用哪个令牌）。
- **`423` 的应答也是坏的**：我们的 423 响应体里嵌的就是 `lockDiscoveryXml(...)`（`src/webdav/index.ts:189-197`），
  所以「被别人的锁挡住 → 读响应发现锁 → 解除」这条**自救路径对规范客户端同样走不通**，只能改用
  从 `Lock-Token` 头拿令牌的路径（即必须在建锁那一刻就记住头，而不是事后发现）。
- **对我们自己的探针/脚本无感**：自研脚本的**主路径**都直接用 `Lock-Token` 头（形态正确），
  所以 `scripts/rfc-probe.mjs` 与 `scripts/webdav-litmus.mjs` 从未发现这条 —— litmus 的 `locks`
  套件在本站因 `MKCOL` 跑不起来，也覆盖不到。**这是「真 litmus 跑不了」的实际代价的一个具体样本。**
- **顺带发现：`scripts/webdav-litmus.mjs` 的 423 兜底路径是死的**（同一根因的下游症状，
  建议顺手修，但别和上面的锁令牌修法混在一起）。该脚本 `:171-174` 在 LOCK 收 423 时想
  「从 lockdiscovery 里提取 token 供后续 unlock」：
  ```js
  const m = body.match(/<urn:uuid:[0-9a-f-]+/);
  if (m) { lockToken = m[0]; ok = true; }
  ```
  但服务端 `escapeOwner()` 会把 token 转义成 `&lt;urn:uuid:…&gt;`（`src/lib/locks.ts:354`），
  实际响应体里是 `&lt;urn:uuid:` —— **正则 `/<urn:uuid:.../` 永远匹配不到**，`ok` 保持 false。
  （本地已用 node 复刻该响应体验证：匹配结果为 `null`。）修法：正则改为
  `/(?:&lt;|<)urn:uuid:[0-9a-f-]+/` 并剥掉转义前缀；若采纳 §4.6.4 的修法 1（裸 token），
  则此处直接匹配裸 URI 即可、同时应去掉 `ok = true` 的掩盖式赋值（它会把失败伪装成成功）。
- **与发现 A（4.1）、4.5（令牌匿名可读 / 第三方可解他人锁）叠加**：既然令牌匿名可读，
  这把「读到 href 却解不掉锁」的账，两边都记在同一处 —— `lockdiscovery` 的 `locktoken` 既
  不该匿名可读，也不该给出不能用的形态。

### 4.6.4 修法建议（一行级，等 Lead 分派；我没有改任何源码）

1. **正本清源**：`newLockToken()` 返回**裸** `urn:uuid:…`（符合 §14.7 的 absolute-URI），
   出口处该加括号的**只有 `Lock-Token` 头**（§10.5 的 Coded-URL 形态）——即 `handleLock`
   与 423 响应的 `'lock-token': \`<${lock.token}>\``。这样：`If:` 头的 `(<urn:uuid:x>)` 抓取
   与 `Lock-Token: <urn:uuid:x>` 比较都用裸串，`href` 输出裸串，三处同时正确。
2. **兼容存量**：DB 里已有带括号的历史行（可能仍在 TTL 内），建议比较时两侧都做一次
   `stripBrackets()` 归一（`value.replace(/^<|>$/g, '')`），而不是直接改存储格式。
3. **最小改动版**（若不想动存储）：只把 ② 的 `href` 输出改成剥括号
   （`escapeOwner(lock.token.replace(/^<|>$/g, ''))`），服务端比较逻辑全部不动。
   代价：`href` 与 `Lock-Token` 头/DB 三种形态不一致，后续维护者仍需知道这个坑。

**方法论注记**：这条能挖出来，靠的是**先读客户端源码（neon）再写复现**——`ne_locks.c` 两条
路径的括号处理不对称是唯一线索；同时必须用**标准 XML 解析器**（Python ElementTree）读
`href`，因为 curl 看到的原文是转义过的 `&lt;…&gt;`，肉眼容易误判成「正常」。

### 4.6.5 ⚠️ 附带后果：`docs/rfc-compliance.md:56` 的 ✅ 是**假阳性**，且它的判据是循环论证

现有文档已把这一条标为合规 —— 而这正是它长期存活的原因：

```
docs/rfc-compliance.md:56
| §14.14 | href 内是锁令牌 URI | 转义后写入，解析还原即裸 URI，与 `Lock-Token` 头一致 | ✅ |
docs/rfc-compliance.md:57
| §6.5 / §10.5 | `Lock-Token: "<" absolute-URI ">"` | 带尖括号形式 | ✅ |
```

- §14.14 的原文（`refs/rfc4918.txt:4711-4720`）：「The href contains a **single lock token URI**,
  which refers to the lock. `<!ELEMENT locktoken (href) >`」，且 §9.10.7 的例子是**裸** URI（见 4.6.1）。
  所以「href 是锁令牌 **URI**」= 裸 `urn:uuid:…`，不含 Coded-URL 的尖括号。
- 文档把判据写成「**与 `Lock-Token` 头一致**」——这是**循环论证**：它拿「与我们自己的头部形态一致」
  当合规标准，而 §10.5 恰恰规定头部**必须**带括号、§14.7/§14.14 规定 XML 里**必须**是 URI 本体。
  两者本来就不该相同；「相同」正是 bug 的表现。
- 结果：**一条真实的互操作缺陷被记为 ✅**，于是没有任何测试或复审去碰它
  （`test/lock-xml.test.ts` 按 DTD 校验元素名/顺序，但不校验 href 的**取值形态**）。
  这是「文档标 ✅ → 无人复核 → 缺陷长期存活」的完整闭环，比缺陷本身更值得记一笔。

**建议**（属 task-10 的文档写范围，我没有改）：把 :56 的 ✅ 改为 ⚠️ 并写明 §14.14 的真实判据，
另把 :57 那句注释补上「头部带括号、XML 里不带」的对照，避免下一位读者再次把「两边一致」当目标。

### 4.6.7 修发现 E 的**测试面影响**（给接手者省一轮推导）

采纳 4.6.4 的**修法 1**（token 存裸串、只在头部出口加括号）后，需要同步调整的断言：

**必须补的新断言**（本次缺口，建议随修一起加）：
