## 二、🔴 高危缺陷

### 2.1 LOCK 响应不是合法 XML —— 严格客户端全部挂

**实测证据**（修复前，线上原文 + .NET 严格解析）：

```xml
<D:locktoken><D:locktoken><D:href>&lt;urn:uuid:…&gt;</D:href></D:locktoken>
```

```
❌ The 'D:locktoken' start tag on line 2 position 331 does not match
   the end tag of 'D:lock'. Line 2, position 465.
```

**规范依据**：[RFC 4918 §8.2](https://www.rfc-editor.org/rfc/rfc4918.txt)

> All XML used in either requests or responses MUST be, at minimum, well formed and use namespaces correctly.

标签开了两次只关一次。**Windows 资源管理器 / RaiDrive / Cyberduck 等用 .NET、Java、
Python 解析器的客户端在 LOCK 时会直接报错**。

同时发现第二处同类缺陷：423 冲突响应把 `<D:lockdiscovery>` 嵌进了自己里面。

**已修**，`test/xml-wellformed.test.ts` 持续兜底。线上复验：`.NET XmlDocument` 解析通过。

### 2.2 `Timeout` 请求头从未被解析

**规范依据**：[RFC 4918 §10.7](https://www.rfc-editor.org/rfc/rfc4918.txt)

```
TimeType = ("Second-" DAVTimeOutVal | "Infinite")
DAVTimeOutVal = 1*DIGIT
```

真实写法是 `Second-300`。而代码的正则是 `/Second-N=(\d+)/` ——
**把 BNF 里的占位符 `N` 当成了字面量**，于是：

- `Second-300` 匹配不上 → 静默退回默认值 300 秒
- 客户端请求 `Second-604800`（一周）也只拿到 300 秒
- **大文件同步到一半锁就过期**，客户端行为不可预期

**已修**，改为 `/^Second-(\d+)$/` 并支持 RFC 允许的逗号候选列表。线上实测 `Second-777` 被真实采纳。

### 2.3 宣告 `DAV: 3` 是不实声明

**规范依据**：[RFC 4918 §18.3](https://www.rfc-editor.org/rfc/rfc4918.txt)

> Advertising class 3 support in addition to class 1 and 2 means that the server supports all the requirements in this specification.

宣告 `3` 等于声称「满足 RFC 4918 全部 MUST」。而本服务有三条 MUST 不满足
（MKCOL 不真正创建集合、PROPPATCH 不持久化、DELETE 集合不支持）。

这不只是文档问题：客户端据此判断服务端能力，不实声明会导致**难以排查的兼容性故障**。

**已修**：改为 `DAV: 1, 2`（§18.2 定义的 Class 2 = Class 1 + 锁，本服务确实实现了）。

## 三、🟠 中危缺陷

| # | 规范依据 | 问题 | 修复 |
|---|---|---|---|
| 1 | §9.3「If the Request-URI is already mapped to a resource, then the MKCOL **MUST fail**」 | 对已存在的集合返回 201，谎报创建成功 | 已映射 → **405**；未映射 → **403 + `valid-resourcetype`**（RFC 5689 §3.1） |
| 2 | §9.2「Instructions **MUST either all be executed or none executed**」、§9.2.1 | PROPPATCH 回 `200 OK` 却什么都不写 —— **虚假成功**，客户端会据此缓存「已设置」 | 改为 **207 + 403 + `cannot-modify-protected-property`**，并报出具体属性名 |
| 3 | §9.6.1「The DELETE method on a collection **MUST** act as if a `Depth: infinity` header was used」 | 集合 DELETE 一律 405，不支持递归删成员 | 实现**递归删除该桶全部书**（分批 + 游标翻页）。**根目录保留 405** |
| 4 | — | `docs/rfc-compliance.md` 与代码严重脱节（写着 `DAV: 1, 3`、LOCK → 501） | 整篇按代码与 RFC 原文重写 |

### 关于「DELETE 根目录」为什么是例外

§9.6.1 要求集合 DELETE 递归删成员。根目录 `/dav/` 的「成员」就是**整个书库**。

实现它意味着：一次手滑、一次客户端 bug、或一条错误的 rclone 同步命令，
就可能**不可逆地清空整个书库**。DELETE 虽已受写口令保护，但口令通常会被写进
rclone 配置文件，`rclone sync` / `purge` 是日常操作。

**取舍**：支持「删具体桶」（§9.6.1 语义），拒绝「删根目录」。批量清理走管理后台
`/admin`（有独立确认流程）。这是有意的安全偏离，已在文档中明确标注。

## 四、🟡 低危 + 一个重要的方法论教训

### 4.1 教训：验证 XML 不能用字符串包含

这是本次审查最有价值的发现。

原测试写法：
```js
expect(xml).toContain('<D:lockdiscovery>')   // ← 坏 XML 也能通过
```

坏掉的响应里**确实含有**这个字符串，所以测试一路绿灯。

> **任何「用字符串匹配验证 XML 结构」的测试都是无效的。**

修正后的做法（`test/xml-wellformed.test.ts`）：
1. 先拿**线上抓到的真实坏样本**证明检查器确实会报错（自检）
2. 再对每个产出 XML 的接口逐条做严格的标签配对校验
3. 用 .NET `XmlDocument` 与测试实现交叉验证

**过程中还发现 `HTMLRewriter` 不可用作检查器**：它是 HTML 解析器（lol-html），
HTML 允许标签不闭合，对 `<a><a></a>` 和真实坏样本都返回「合法」——
**假通过的检查器比没有检查器更危险**（会被无视，或者掩盖真问题）。

### 4.2 其他低危项

| # | 问题 | 修复 |
|---|---|---|
| 1 | `getetag` 被 XML 转义成 `&quot;abc&quot;` | entity-tag 是 ASCII token（§15.6），转义后客户端 `If-Match` 对不上服务端。改为不转义 |
| 2 | 文件名清洗**不是单射**：`a*b.epub` 与 `a?b.epub` 都变成 `a_b.epub` | 记录为已知取舍并加测试。影响：两本不同的书可能共用一个 `leaf_name`，后传的会覆盖前者元数据 |

## 七、架构与成本审查

| 项 | 评价 |
|---|---|
| 目录树「宽而浅」 | ✅ 合理。目录总数上界约 120，远低于 200 的设计上限，避免请求数爆炸 |
| PROPFIND 只读 D1，不用 `R2.list()` | ✅ **关键决策**。否则每次列目录都要扫描 R2，Class B 操作会打爆 1000 万/月 |
| GET 返回 302 到 R2 公共域 | ✅ 字节完全不过 Worker：不占 CPU/内存，不受 100 MB 限制 |
| 写入节流用 Cache API 而非 D1 | ✅ 正确。D1 每次写一行，自己就把 10 万/天的写入配额吃光了 |
| 拼音表 63 KiB 烘成静态表 | ✅ 开发期生成、运行零依赖，权衡得当 |
| **节流是尽力而为** | ⚠️ Cache API 按数据中心计数，多边缘节点不共享；读-改-写非原子。**是减速带，不是配额系统** |
| **无速率限制的 WebDAV 通道** | ⚠️ 匿名 + 无验证码。恶意脚本可批量上传至每日 300 次上限 |
